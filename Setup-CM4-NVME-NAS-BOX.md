# Setup CM4 + CM4-NVME-NAS-BOX

## What this document covers

This document covers:

- installing and booting a Raspberry Pi CM4 (32 GB eMMC) in the Waveshare CM4-NVME-NAS-BOX enclosure,
- fan control setup,
- Cockpit web interface setup,
- installing the two M.2 SSDs.

Setting up the dual-SSD storage (Btrfs or mdadm RAID 1) is covered in [Setup NAS disks](./Setup-NAS-disks.md).

The procedure keeps the OS on the Raspberry Pi's internal eMMC, using Raspberry Pi OS (Debian 12 "Bookworm").

## 1. Hardware

> **Important**: use a stable 5 V / 3 A power supply. With insufficient power, the PCIe switch (and with it the USB-A ports) may fail to initialize once the SSDs are installed. Start the installation with both M.2 slots empty. The SSDs are only installed in step 7, once the system is stable and the power supply is validated.

- CM4 with 32 GB eMMC, firmly seated in the enclosure.
- 5 V USB-C power supply, 3 A or more, with a short, good-quality cable.
- **Empty M.2 slots** for steps 2 to 6.
- **BOOT** switch on the enclosure:
  - **ON**: USB mode, used to flash the eMMC from a PC.
  - **OFF**: normal boot from the eMMC.

## 2. Flash the eMMC with rpiboot

### Install the tools (on the Linux PC)

Install `rpiboot` and `rpi-imager`:

```
sudo apt install rpiboot rpi-imager
```

If the `rpiboot` package is not available on your distribution, build it from source:

```
sudo apt install git libusb-1.0-0-dev pkg-config build-essential
git clone --recurse-submodules --shallow-submodules --depth=1 https://github.com/raspberrypi/usbboot
cd usbboot && make
sudo ./rpiboot
```

### Flash the eMMC

To flash the OS in the RPi internal eMMC:

1. Power off the enclosure and set the BOOT switch to **ON**.
2. Connect the flashing USB-C port to the Linux PC, then power on the enclosure.
3. Run:

   ```
   sudo rpiboot
   ```

   When it finishes, the eMMC appears as a USB disk. Check its name with `lsblk` (for example `/dev/sdX`, about 29 GB).
4. Write Raspberry Pi OS to this disk, with one of these methods:
   - **Raspberry Pi Imager**: run `rpi-imager`, choose the device **Raspberry Pi 4**, the OS **Raspberry Pi OS Lite (64-bit)**, in its **Bookworm** version (under "Raspberry Pi OS (other)"; a fresh download now defaults to a newer release, and this guide was written for Bookworm), and the eMMC as storage. Skip the OS customisation if you follow section 3 instead.
   - **`dd`**: download the Bookworm Lite 64-bit `.img.xz` image from raspberrypi.com, then write it. **Check the target with `lsblk` first**: replace `sdX` with the eMMC (about 29 GB), because a wrong name erases another disk, possibly the PC's own:

     ```
     xzcat <image>.img.xz | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress
     ```

   You get two partitions: `bootfs` and `rootfs`. If they are not mounted automatically after writing, mount them from your file manager (section 3 expects them under `/media/$USER/`).

## 3. Prepare headless access (no screen or keyboard)

With the eMMC still visible on the PC, from the `bootfs` partition:

```
touch /media/$USER/bootfs/ssh
echo "pi:$(openssl passwd -6 'password')" > /media/$USER/bootfs/userconf.txt
```

- `ssh` (an empty file) enables SSH on first boot.
- `userconf.txt` creates the user and its password (Raspberry Pi OS Bookworm no longer ships a default user). Replace `pi` and `password` with your own choice.

If the user already exists and you need to change its password, replace the second field of its line in `etc/shadow` on the `rootfs` partition with a hash generated by `openssl passwd -6`.

## 4. Boot files

**`cmdline.txt`** (on `bootfs`, a single line):

```
console=serial0,115200 console=tty1 root=PARTUUID=<PARTUUID> rootfstype=ext4 fsck.repair=yes rootwait
```

- `<PARTUUID>` must match the one of the `rootfs` partition (check with `blkid`, `PARTUUID` field of the `rootfs` partition). Do not copy a value from another system.
- You can remove `quiet splash plymouth.ignore-serial-consoles` to see boot messages on an HDMI screen.

**`config.txt`** (on `bootfs`), `[cm4]` section:

```
[cm4]
#otg_mode=1
dtoverlay=dwc2,dr_mode=host
```

The default file is fine. Waveshare asks for `dwc2` in host mode for the CM4's USB 2.0, and recommends not using `otg_mode=1`. No other change is needed to boot. The fan is configured as an option (see below).

### Fan (GPIO19)

The enclosure controls its fan with the CM4's **GPIO19** pin. The Waveshare documentation says nothing more: it does not state the fan type (2, 3 or 4 wires), the signal polarity, or whether it accepts a PWM command. So test by hand before configuring anything.

**Manual test** (the fan should change state with each command):

```
pinctrl set 19 op dh   # output driven high
pinctrl set 19 op dl   # output driven low
```

- If the fan runs when high and stops when low, it is controlled on/off with normal polarity: use option 1.
- If it behaves the other way around, the polarity is inverted (the `gpio-fan` overlay of option 1 does not fit as-is).
- A reboot restores the pin to its original state.

To monitor the CPU temperature:

```
vcgencmd measure_temp
```

#### Option 1: on/off depending on temperature

The `gpio-fan` driver turns the fan on above a temperature and off when it drops back down. Add to `config.txt`, in the `[all]` section (at the end):

```
dtoverlay=gpio-fan,gpiopin=19,temp=60000,hyst=10000
```

- `gpiopin=19`: the fan pin (the overlay's default is 12, so it must be specified).
- `temp=60000`: turn-on threshold in millidegrees Celsius (here 60 °C).
- `hyst=10000`: temperature gap before turning off (here it turns off around 50 °C).

Reboot, then check:

```
cat /sys/class/thermal/cooling_device*/type
```

The list must contain `gpio-fan`.

#### Option 2: variable speed (PWM)

GPIO19 is a hardware PWM output (channel PWM1, function ALT5). With a 4-wire fan, you can adjust its speed instead of only turning it on or off. Do not combine this option with option 1 on the same pin.

**PWM audio and GPIO19: no conflict on this enclosure.** On basic Raspberry Pi boards and enclosures, the Pi's analog (PWM) audio output can be routed to GPIO18 and GPIO19 (the `pins_18_19` option of the `audremap` overlay). Using those pins for a PWM fan then conflicts with the audio. This enclosure is different: its sound comes from a **dedicated USB audio chip** (a JMTek codec, USB ID `0c76:161f`, visible in `lsusb` as `USB PnP Audio Device`), and the Waveshare wiki and schematic show no PWM audio connection on GPIO19. GPIO19 is therefore free for PWM fan control, and the enclosure's audio keeps working.

Leave the default `dtparam=audio=on` line of `config.txt` as it is. If `pwmchip0` does not appear in the check below, or the PWM output misbehaves, try `dtparam=audio=off` and reboot. This fallback is untested on this enclosure: the enclosure itself does not use the CM4's analog audio driver, but I could not confirm that the driver never interferes with PWM on GPIO19.

1. Add to the end of `config.txt`, in the `[all]` section:

   ```
   dtoverlay=pwm,pin=19,func=2
   ```

   `func=2` selects the ALT5 function of GPIO19, which corresponds to PWM channel 1.

2. Reboot, then check:

   ```
   ls /sys/class/pwm/
   dmesg | grep -i pwm
   ```

   `pwmchip0` must appear.

**Speed test** (period of 40,000 ns, i.e. 25 kHz, the standard frequency for 4-wire fans; channel 1 corresponds to GPIO19):

```
echo 1 | sudo tee /sys/class/pwm/pwmchip0/export
echo 40000 | sudo tee /sys/class/pwm/pwmchip0/pwm1/period
echo 20000 | sudo tee /sys/class/pwm/pwmchip0/pwm1/duty_cycle
echo 1 | sudo tee /sys/class/pwm/pwmchip0/pwm1/enable
```

`duty_cycle` must always stay less than or equal to `period`: 20,000 corresponds to 50 % speed. Change this value to try other speeds. If the fan runs at full speed when you expect the minimum, the polarity is inverted.

**Adjusting the speed according to temperature.** The sysfs settings are lost at each reboot, so a small service is needed. Create `/usr/local/bin/fan-pwm.sh`:

```
#!/bin/bash
CHIP=/sys/class/pwm/pwmchip0
CH=1
PERIOD=40000   # 25 kHz

[ -d $CHIP/pwm$CH ] || echo $CH > $CHIP/export
echo $PERIOD > $CHIP/pwm$CH/period
echo 1 > $CHIP/pwm$CH/enable
# If the script stops, set the fan back to full speed
trap 'echo $PERIOD > $CHIP/pwm$CH/duty_cycle' EXIT

while true; do
  raw=$(cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null)
  t=$(( ${raw:-100000} / 1000 ))   # if the read fails, assume hot: full speed
  if   [ $t -lt 45 ]; then pct=0
  elif [ $t -lt 55 ]; then pct=40
  elif [ $t -lt 65 ]; then pct=70
  else pct=100
  fi
  echo $(( PERIOD * pct / 100 )) > $CHIP/pwm$CH/duty_cycle
  sleep 5
done
```

Then create `/etc/systemd/system/fan-pwm.service`:

```
[Unit]
Description=Fan PWM control (GPIO19)

[Service]
ExecStart=/usr/local/bin/fan-pwm.sh
Restart=always

[Install]
WantedBy=multi-user.target
```

And enable it:

```
sudo chmod +x /usr/local/bin/fan-pwm.sh
sudo systemctl daemon-reload
sudo systemctl enable --now fan-pwm.service
```

The thresholds (45, 55 and 65 °C) and the percentages are starting values to adjust for your fan. Some fans never stop completely at 0 %. This script has not been tested on this enclosure: check that it is running (`systemctl status fan-pwm.service`) and watch the temperature at first. Stopping the service can take up to 5 seconds (the loop finishes its `sleep`), then the fan goes back to full speed.

## 5. First boot

1. Unmount the eMMC cleanly (`sync`, then eject).
2. Set the BOOT switch to **OFF** and unplug the USB flashing cable.
3. Plug in the Ethernet cable and power the enclosure (M.2 slots still empty).
4. Find the IP address in your router's DHCP list.
5. Connect:

```
ssh pi@<ip_address>
```

## 6. System update

```
sudo apt update && sudo apt full-upgrade -y
sudo reboot
```

The kernel moves to the latest Bookworm version (6.12.x). Updating the CM4's EEPROM is not necessary. If you do it later, use `rpiboot`: `rpi-eeprom-update` is disabled on CM4.

### Check PCIe (without disks)

```
sudo lspci
```

The output must list the CM4's PCIe bridge, the ASMedia ASM1184e switch (several ports), the VIA VL805 USB controller and the Realtek RTL8111 Ethernet controller. The USB-A ports then work (keyboard, etc.).

## 7. Add the M.2 disks

Once the system boots correctly, `lspci` is complete and the power supply is validated:

1. Power the enclosure off completely (`sudo poweroff`, then unplug the power supply).
2. Install **a single SSD**, power on, then check:

   ```
   sudo lspci
   lsblk
   dmesg | grep -i -E "nvme|pcie|d3cold"
   ```

3. If everything is recognized, power off, add the second SSD, power on and check again.

You must see each SSD in `lspci` (NVMe controller) and in `lsblk` (`nvme0n1`, `nvme1n1`), with no `d3cold` error in `dmesg`.

If the system no longer boots, or if the PCIe switch becomes inaccessible after adding an SSD, power off, remove the SSD concerned and check the power supply (5 V, 3 A or more). A power-hungry SSD can prevent the PCIe switch from initializing.

## 8. Install Cockpit (web administration interface)

Cockpit provides a web interface to monitor and administer the Raspberry Pi: system status, services, logs, updates, network, terminal and storage.

### Installation

```
sudo apt update
sudo apt install cockpit
```

The service starts automatically and runs at every boot through `cockpit.socket`. Check it:

```
systemctl status cockpit.socket --no-pager
```

The `cockpit` package also installs the usual modules (system, network, updates, storage with `cockpit-storaged`).

### Connect from a web browser

1. From a computer on the same network, open in a browser:

   ```
   https://<raspberry_ip_address>:9090
   ```

   If the host name is recognized on your network, `https://raspi:9090` works too (`raspi` is your system's host name).

2. The browser shows a **certificate warning**. This is normal: Cockpit uses a self-signed certificate. Accept the exception ("Advanced", then "Continue").

3. Log in with your Linux user (the one created with `userconf.txt`, for example `pi`) and its password.

4. To perform administration actions (install packages, manage services, storage), click **"Limited access"** at the top of the page, switch to administrative access, and confirm with your password. The user must belong to the `sudo` group (this is the case for the main user of Raspberry Pi OS).

### Notes

- Port **9090** is open over HTTPS. No firewall is active by default on Raspberry Pi OS, so Cockpit is reachable from your whole local network.
- **Do not expose port 9090 directly to the Internet** (port forwarding on your router). For remote access, use a VPN instead (WireGuard, Tailscale or your router's).
- On a Btrfs RAID 1 volume, the Storage page may show an "Inconsistent filesystem mount" warning for the second disk. This is a known display problem of Cockpit with multi-device Btrfs filesystems, with no effect on how the volume works.

- [CM4-NVME-NAS-BASE schematic (PDF)](https://files.waveshare.com/upload/b/b1/CM4-NVME-NAS-BASE-SchDoc.pdf): audio nets (`HPOUT_L/R`, `MIC_L/R`) routed through USB, and no audio or PWM-audio nets on GPIO12/13/18/19/40/41.
- [CM4-IO-BASE-C, Waveshare Wiki](https://www.waveshare.com/wiki/CM4-IO-BASE-C) and [product page](https://www.waveshare.com/cm4-io-base-c.htm): BOOT switch behavior (ON = USB boot for flashing, OFF = normal boot). The NAS-BOX wiki does not describe its BOOT switch; this behavior was confirmed on the enclosure itself (the CM4 only appeared as a USB device with the switch ON).
- [raspberrypi/firmware issue #1684](https://github.com/raspberrypi/firmware/issues/1684): the CM4 bootloader cannot boot from an NVMe behind a PCIe switch/bridge, which is why the system stays on the eMMC.
- [cockpit-project/cockpit issue #20743](https://github.com/cockpit-project/cockpit/issues/20743): Cockpit shows the second device of a Btrfs RAID 1 as unmounted. - [Enabling Hardware PWM on Raspberry Pi, dotnet/iot](https://github.com/dotnet/iot/blob/main/Documentation/raspi-pwm.md): GPIO19 as PWM1 (ALT5, `func=2`), the `dtoverlay=pwm,pin=19,func=2` syntax, and the sysfs path under `/sys/class/pwm/pwmchip0`.
